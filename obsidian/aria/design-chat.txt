1. Yes, the 3-day gap before support confirms creates a real effectiveness problem.

Currently check_assignment_eligibility blocks new account requests if any account is in "escalated" status. That means:

Day 0: gamer finishes an account
Days 1–2: warnings pile up
Day 3: account escalated to support → gamer is now blocked
Day 3+N: support eventually decides → gamer is unblocked
During that entire support review window (which could be another day or more), the gamer is idle with no ability to get new work. That's the wrong incentive — you want gamers playing, not waiting.

The fix is simple: remove the escalation check from eligibility entirely. An escalated account is already being handled by support out-of-band — it shouldn't block the gamer from requesting a new productive account. The two processes run in parallel:

python
# Remove this check from check_assignment_eligibility:
if account.get("status") == "escalated":
    return False, f"Аккаунт {account['profile']} на рассмотрении поддержки"
The escalation resolves independently. Support makes a decision, account gets disposed, done.

2. Yes, the 18h formula overcounts calendar days — your example is exactly right.

June 1 12:00 → June 3 18:00 = 54 hours. 54 ÷ 18 = 3, so the code says "3 days inactive" — but only 2 calendar days passed. The formula can fire escalation a full day early.

The 18h buffer was meant to handle the 16:00/12:00 update timing, but it's solving the wrong problem. The right fix is to just use calendar date arithmetic:

python
# Replace this:
elapsed_seconds = (datetime.utcnow() - baseline).total_seconds()
days_inactive = int(elapsed_seconds // boundary_seconds)

# With this:
days_inactive = (datetime.utcnow().date() - baseline.date()).days
This is both simpler and correct for all cases:

June 1 16:00 → June 2 10:00: date diff = 1 ✓ (counts as next day even at 18h gap)
June 1 12:00 → June 3 18:00: date diff = 2 ✓ (correctly 2 days, not 3)
June 1 16:00 → June 1 23:59: date diff = 0 ✓ (same day, no warning)
The inactivity_day_buffer_hours config field becomes unnecessary and can be dropped.

EC-2 — Missing TP Start entirely. Accounts near the end of the sheet have fewer than 8 columns — the row ends after proxy. These are accounts with no Season 1 data. len(account) < 8 must be caught and treated as season3_start_points = 0.

EC-3 — Active column semantics. Active (col 5) = #N/A means the account is NOT active in Season 3. Should the synchonizer skip these entirely, or import them as inactive/unassigned? If skipped, they'd never appear in the pool for assignment.

EC-4 — Season 3 Profiles tab. There's a dedicated Season 3 Profiles sheet listing the canonical S3 account set. Using this as a filter is cleaner than relying on col 5 (#N/A) — it's a whitelist vs. a per-row flag. Either the synchonizer reads this tab first and filters, or it relies on Active != #N/A. These two might disagree.

EC-5 — Where does automation write current tower points? With Option C, the sheet is a data source. When Octo+Puppeteer automation eventually runs and scrapes live tower points — which column does it write to? If it overwrites col 7 (TP Start), the Season 3 baseline is destroyed. EC-6 — "5 released" constraint ambiguity. You said: "if gamer has 5 released and available for play accounts we decline account requests." This could mean:

(a) Gamer previously owned 5 accounts that are currently available_for_pickup=True (sitting in pool after being released)
(b) Gamer has had 5 total releases over the season (cumulative, regardless of current pool state)
These are very different. (a) means: you caused congestion in the pool, clean it up first. (b) means: you're a repeat offender. Which one?

EC-7 — Pool priority and "non-participating gamer" query. Finding accounts owned by gamers with zero currently active accounts requires two DB queries: (1) find all gamer_ids who have at least one status=active account, (2) find accounts whose gamer_id NOT IN that set. MongoDB doesn't do cross-collection joins without $lookup aggregation. Options:

Application-level: fetch all active gamer_ids first, then query accounts where gamer_id not in [list] — works fine at current scale
Aggregation pipeline with $lookup
Denormalized flag active_account_count on gamer document (most efficient, needs maintenance)
At guild scale (dozens of gamers, ~100-200 accounts) the application-level approach is fine. Confirm this is acceptable.

EC-8 — Best account selection metric for auto-assign. When the pool has multiple available accounts, which gets assigned? Options:

Highest season3_start_points (strongest established account, most S1 history)

C3 — 1 account pickup per day (no-progress block)
Rule in plain language: If a gamer picked up an account today and hasn't received a single positive-delta sync on it, they cannot pick up another.

Implementation: add picked_up_at to the account document.

This is the cleanest approach. The field is set atomically during pickup and gives us a datetime to compare against progress history:

python
async def check_daily_pickup_block(gamer_oid, accounts_today):
    """
    Returns (blocked: bool, account_profile: str|None).
    Blocked if any account assigned today has no positive-delta progress entry since pickup.
    """
    for account in accounts_today:
        picked_up_at = account.get("picked_up_at")
        if not picked_up_at or picked_up_at.date() != datetime.utcnow().date():
            continue
        # Any positive progress entry after the pickup?
        progress_since = [
            e for e in account.get("progress_history", [])
            if e["synced_at"] > picked_up_at and e["delta"] > 0
        ]
        if not progress_since:
            return True, account["profile"]
    return False, None
⚠️ Open Question Q4: What counts as "progress" for the daily block?

Option A delta > 0 — any positive tower change, even 1 point.
Option B delta >= min_progress_points — must clear the configured threshold (currently 50 points). Consistent with the rest of the system's definition of "good progress."
I'd recommend Option B for consistency — a 1-point fluctuation shouldn't unlock a second pickup.

async def check_assignment_eligibility(self, gamer_object_id: ObjectId, config: dict):
    """
    Returns (eligible: bool, reason: str).
    Gamer is eligible for a new account when:
      1. Occupied slots (active + escalated + pending_release) < max_accounts_per_gamer
      2. All strictly active accounts have progress_history[-1].gamer_id == this gamer
         AND progress_history[-1].delta >= min_progress_points
         (escalated and pending_release accounts are excluded)
    """
    occupied = await self.db.accounts.find({
        "gamer_id": gamer_object_id,
        "status": { "$in": ["active", "escalated", "pending_release"] }
    }).to_list(None)

    max_accounts = config.get("max_accounts_per_gamer", 10)
    if len(occupied) >= max_accounts:
        return False, f"Достигнут лимит аккаунтов ({max_accounts})"

    min_progress = config.get("min_progress_points", 50)
    for account in occupied:
        if account["status"] != "active":
            continue  # escalated and pending_release are exempt
        history = account.get("progress_history", [])
        if not history:
            return False, f"Аккаунт {account['profile']} — нет данных о прогрессе"
        last = history[-1]
        if last.get("gamer_id") != gamer_object_id:
            return False, f"Аккаунт {account['profile']} — ожидаем синхронизацию под вашим владением"

            return False, f"Аккаунт {account['profile']} — недостаточно прогресса (нужно {min_progress}+ очков башни)"

    return True, "ok"

async def pickup_account(self, gamer_object_id: ObjectId) -> dict | None:
    """
    Auto-assign the best available account to this gamer.

    Priority 1: accounts ever owned by this gamer (any ownership_history entry),
                sorted descending by tower.points.
    Priority 2: accounts whose last owner has never picked up this season
                (season_picked_up not True), sorted descending by tower.points.
                Accounts with no previous owner (ownership_history empty) are
                also included here.

    Assignment is atomic — findOneAndUpdate with status=="released" guard prevents
    two gamers from claiming the same account.
    """
    now = datetime.utcnow()

    # --- Priority 1 ---
    p1 = await self.db.accounts.find({
        "status": "released",
        "ownership_history.gamer_id": gamer_object_id,
    }).sort("tower.points", DESCENDING).to_list(None)

    # --- Priority 2 (accounts not in P1) ---
    p1_ids = { a["_id"] for a in p1 }
    remaining = await self.db.accounts.find({
        "status": "released",
        "_id": { "$nin": list(p1_ids) },
    }).to_list(None)

    # Partition remaining by whether their last owner is inactive this season
    prev_owner_ids = []
    for acc in remaining:
        oh = acc.get("ownership_history", [])
        if oh and oh[-1].get("gamer_id"):
            prev_owner_ids.append(oh[-1]["gamer_id"])

    inactive_owners = set()
    if prev_owner_ids:
        active_owners = await self.db.gamers.find({
            "_id": { "$in": prev_owner_ids },
            "season_picked_up": True,
        }).to_list(None)
        active_owner_ids = { g["_id"] for g in active_owners }
        inactive_owners = set(prev_owner_ids) - active_owner_ids

    p2 = []
    for acc in remaining:
        oh = acc.get("ownership_history", [])
        last_owner_id = oh[-1]["gamer_id"] if oh and oh[-1].get("gamer_id") else None
        if last_owner_id is None or last_owner_id in inactive_owners:
            p2.append(acc)
    p2.sort(key=lambda a: a.get("tower", {}).get("points", 0), reverse=True)

    # --- Attempt atomic claim in priority order ---
    for account in p1 + p2:
        result = await self.db.accounts.find_one_and_update(
            { "_id": account["_id"], "status": "released" },
            {
                "$set": {
                    "gamer_id": gamer_object_id,
                    "status": "active",
                    "last_notified_day": None,
                    "escalated_at": None,
                },
                "$push": {
                    "ownership_history": {
                        "gamer_id": gamer_object_id,
                        "assigned_at": now,
                        "released_at": None,
                    }
                },
            },
            return_document=True,
        )
        if result:
            return result

    return None

6. migration_season4.py — new script
The script must be idempotent. Detection key: account has progress_history with at least one entry and "season3_start_points" not in account. (Checking both avoids re-running on already-migrated Season 4 accounts that legitimately have empty history on first pass.)

For each account in accounts collection:

  Skip if "season3_start_points" not in account
      (already migrated to Season 4 — idempotency guard)

  1. Build seed progress_history entry:
     seed = {
         synced_at: now,
         tower_points: account["season3_start_points"],
         delta: account["season3_start_points"],
         gamer_id: account.get("gamer_id"),        ← credits points to current owner
     }

  2. Build closed ownership_history entry:
     if account.get("gamer_id"):
         oh_entry = {
             gamer_id: account["gamer_id"],
             assigned_at: account["ownership_history"][0]["assigned_at"]
                          if ownership_history else now,
             released_at: now
         }
     else:
         oh_entry = None  (no history to carry)

  3. $set on account:
     {
         status: "released",
         gamer_id: null,
         progress_history: [seed],             ← replaces empty [] (or prepend if non-empty)
         ownership_history: [oh_entry] if oh_entry else [],
         last_progress_at: null,
         last_notified_day: null,
         escalated_at: null,
     }
     $unset:
     {
         season3_start_points: "",
         available_for_pickup: "",
         gamer: "",                             ← Season 1 legacy string field
         pending_proof: "",
         release_request: "",
     }
     $set ownership_history entries: strip gamer_username from each entry
         → rewrite the whole array with gamer_username removed

For each gamer:
  No action needed — season_picked_up defaults to absent (falsy).
  ensure_indexes() will add the sparse index at bot startup.
Important nuance on progress_history during migration: If an account already has Season 3 progress entries (syncs ran during Season 3), prepend the seed rather than replacing. The seed becomes progress_history[0], existing entries follow. This preserves Season 3 earning history.
